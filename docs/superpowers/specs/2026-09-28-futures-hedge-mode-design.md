# 선물 양방향(헤지) 매매 · 일부 청산 설계 (2026-09-28)

## 배경

- 사용자 요청 1: 선물도 현물처럼 보유 물량 일부만 청산하고 싶다. 주문 패널에서 반대 방향 주문으로 일부 청산은 되지만, 포지션 카드의 청산 버튼은 "전량 청산"뿐이고 주문 패널에서 청산이라는 게 드러나지 않는다.
- 사용자 요청 2: 숏을 들고 있을 때 롱을 사면 숏이 줄어든다. 롱·숏을 동시에 들 수 있게(양방향) 해 달라.
- 지금 구조: `account.futures_positions`가 (계좌, 종목)당 부호 있는 순포지션 하나. 옵션 포지션도 같은 테이블을 쓴다.

## 결정 사항

| 항목 | 결정 |
|---|---|
| 적용 범위 | 사람 계정은 항상 양방향. 봇 계정은 지금처럼 순포지션(단방향). |
| 대상 상품 | 선물만. 옵션은 변경 없음(순포지션 유지). |
| 증거금 | 롱·숏 각각 레버리지 증거금을 따로 묶는다(헤지 상쇄 없음). |
| 레버리지 | 종목당 하나, 롱·숏 공유. 포지션·미체결 주문이 있으면 잠김(지금 규칙). |
| 주문 화면 | [진입 \| 청산] 탭 + [롱] [숏] 버튼. |
| 구현 방식 | 기존 테이블에 `position_side` 칸 추가(방식 A). |

## 데이터 모델

### `account.futures_positions`
- 새 칸 `position_side TEXT NOT NULL DEFAULT 'NET'` — `LONG` | `SHORT` | `NET`.
- 기본키 (account_id, symbol) → (account_id, symbol, position_side).
- 수량 부호 유지: `LONG`은 qty ≥ 0, `SHORT`는 qty ≤ 0, `NET`은 지금처럼 부호 있는 순포지션. 평가 SQL(수량 × 가격 합)은 바뀌지 않는다.
- `leverage`는 행마다 있지만 같은 (계좌, 종목)의 행은 같은 값을 갖도록 레버리지 변경 API가 모든 방향 행을 함께 바꾼다.

### `order.orders`, `order.conditional_orders`
- 새 칸 `position_side TEXT NULL` — `LONG` | `SHORT` | null(순포지션 주문: 봇·옵션·현물).
- 주문의 뜻:

| side | position_side | 뜻 |
|---|---|---|
| BUY | LONG | 롱 진입 |
| SELL | LONG | 롱 청산 |
| SELL | SHORT | 숏 진입 |
| BUY | SHORT | 숏 청산 |
| BUY/SELL | null | 순포지션(지금 동작) |

### 마이그레이션
1. 칸 추가(기본값 `NET`), 기본키 교체.
2. 사람 계정(`auth.users.is_bot = false`)의 선물 포지션(옵션 제외): qty > 0 → `LONG`, qty < 0 → `SHORT`, qty = 0 행은 `LONG`.
3. 사람 계정의 살아 있는 선물 주문·대기 중인 조건부 주문은 방향을 채운다: 현재 포지션을 줄이는 방향이고 잔량이 그 포지션 수량 이하면 그 포지션 방향(청산), 그 밖(포지션 없음·같은 방향·포지션보다 큰 뒤집기 주문)은 진입 방향(BUY→LONG, SELL→SHORT). 뒤집기 주문이 진입으로 바뀌면 그 주문의 증거금 홀드는 이미 진입 기준(청산분 0이 아님)인지 마이그레이션 스크립트가 확인하고, 모자라면 그 주문을 취소 요청한다.
4. 봇 계정과 옵션 행은 `NET` / null 그대로.

## 주문 접수 (API `OrderService.place`)

- 입력에 선택 칸 `positionSide`(`LONG` | `SHORT`) 추가.
- 사람 계정의 선물 주문은 `positionSide` 필수 — 없으면 400 "선물 주문은 롱/숏 방향이 필요합니다". 봇의 선물 주문에 `positionSide`가 오면 400(봇은 순포지션). 옵션·현물 주문에 오면 400.
- 진입 주문: 지금 신규 주문과 같은 레버리지 증거금(+수수료)을 묶는다.
- 청산 주문: 증거금 0. 청산 가능 수량 = |해당 방향 보유| − 해당 방향 청산 미체결 잔량. 주문 수량이 이를 넘으면 422 "청산 가능 수량이 부족합니다". 청산 주문은 반대 포지션을 새로 열지 않는다.
- 시장가 한도·호가 단위·최대 계약 수 규칙은 그대로.
- 레버리지 잠금 판정은 그 종목의 모든 방향 포지션·미체결 주문을 본다.

## 체결 정산 (settlement `settleFuturesTrade`)

- 매수·매도 다리마다 주문 행의 `position_side`로 대상 포지션 행을 고른다(null이면 `NET`).
- 방향 포지션에 적용하는 규칙:
  - 진입: 수량·진입가 합산(`applyFutureFill`과 같은 평균가 계산).
  - 청산: 수량을 줄이고 실현손익 기록. 청산이 보유보다 많게 체결되는 경우는 접수 단계에서 막히므로 없어야 하며, 생기면 보유만큼만 닫고 경고 로그(반대로 열지 않음).
- 같은 계좌가 자기 롱 진입과 숏 진입끼리 체결되면 두 행에 각각 반영.
- `futures_realized`에 방향 칸은 추가하지 않는다(실현손익 합계만 쓰인다). 증거금 해제·현금·미수금·수수료 처리는 그대로.
- 멱등성: `processed_events`로 중복을 버리는 기존 불변식 유지.

## 위험 관리 (`FuturesRiskService`)

- 추가증거금 판단은 지금처럼 계좌 전체(현금 + 평가손익 − 미수금 vs 유지증거금). 증거금 합계는 모든 방향 행 합.
- 기한 초과 비율 반대매매, 긴급 반대매매(평가손실이 그 포지션 증거금의 90%)는 포지션(방향 행)별. 반대매매 주문은 그 방향의 청산 주문(`position_side` = 그 방향)으로, NET 행은 지금처럼 null.

## 일일 정산 (04:11, `FuturesSettlementService`)

- 방향 행마다 결제가로 닫는다. "이미 정산함" 판정 키에 방향을 포함한다.

## 조건부 주문 · 손절·익절

- 조건부 주문에 `position_side` 저장. 선물 청산 가능 수량 검사(`futuresClosable`)와 고아 판정은 방향별.
- 포지션 카드의 손절·익절(OCO)은 그 방향의 청산 주문으로 발동.

## API 응답

- `/account/futures` 포지션 행에 `positionSide` 추가. 롱·숏이 둘 다 있으면 같은 종목이 두 행. 청산 가능 수량 `closableQty`도 행마다 준다.
- 주문 목록 응답에 `positionSide` 포함.
- `docs/api.md` 갱신.

## 웹 화면

### 주문 패널 (`FuturesOrderPanel`)
- 맨 위 [진입 | 청산] 탭.
- 진입 탭: 지정가/시장가, 가격, 수량(주문 가능 금액 기준 % 버튼), 필요 증거금(수수료 포함), 긴급 반대매매 예상 가격, [롱 진입] [숏 진입].
- 청산 탭: "보유 롱 5 · 숏 3 (청산 가능 롱 4 · 숏 3)", 수량(% 버튼은 청산 가능 수량 기준 — 롱·숏이 다르므로 마지막에 고른 방향 기준, 기본은 보유가 있는 쪽), 예상 실현손익, [롱 청산] [숏 청산]. 보유가 없는 방향 버튼은 비활성.
- 기존 매수/매도 탭, 뒤집기 안내 제거.

### 포지션 카드 (`FuturesPositionPanel` · `FuturesPositionActions`)
- 롱·숏을 별도 행으로: 평균가, 수량, 평가손익, 증거금, 긴급 반대매매 가격.
- 청산: 수량 입력 + 25/50/75/100% + [시장가 청산]. "전량 청산" 단일 버튼 대체.
- 손절·익절은 행(방향)별.

### 주문 내역
- 선물 주문은 "롱 진입 / 롱 청산 / 숏 진입 / 숏 청산"으로 표시(position_side 없는 옛 주문은 매수/매도).

### 번역
- ko·en·ja 문구 추가(`apps/web/src/lib/i18n/messages.ts`, 서버 메시지는 `packages/shared/src/server-messages.ts`).

## 봇

- 변경 없음. 봇은 `positionSide`를 보내지 않고 `NET` 행을 쓴다. 봇 클라이언트의 포지션 조회가 방향 칸이 생겨도 깨지지 않는지만 확인.

## 정합성 검사 (`packages/db/scripts/check-consistency.ts`)

- 포지션 증거금 합 검사를 방향 행 단위로.
- 새 검사: LONG 행 qty ≥ 0, SHORT 행 qty ≤ 0, 사람 계정에 선물 NET 행이 없고(qty ≠ 0), 봇 계정에 LONG/SHORT 행이 없다.

## 테스트

- shared: 주문 뜻 판정(진입/청산), 청산 가능 수량, 방향 체결 적용.
- api: 사람 계정 `positionSide` 누락 거절, 봇의 `positionSide` 거절, 청산 수량 초과 거절, 청산 증거금 0, 진입 증거금·수수료.
- settlement: 롱 진입이 숏 행을 건드리지 않음, 한 계좌 롱·숏 동시 체결, 실현손익·증거금 해제·수수료.
- risk·일일 정산: 방향별 긴급 반대매매, 롱·숏 각각 결제가 정산.
- 정합성 검사 새 항목.
- 로컬 검증: 숏 보유 → 롱 진입 → 둘 다 남음, 롱 일부 청산, 포지션 카드 % 청산(`.claude/skills/verify/SKILL.md`, `pnpm smoke`).
