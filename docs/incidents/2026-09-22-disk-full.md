# 2026-09-22 운영 장애: 디스크 고갈

## 원인과 영향

- 루트 파일시스템 45GB가 100%에 도달했다. PostgreSQL 로그에 `could not write to file pg_wal/xlogtemp: No space left on device`가 기록되고 재시작이 반복됐다.
- 미사용 Docker 빌드 캐시 약 14.47GB와 미보관 WAL 약 19GB가 공간을 차지했다. 실제 DB 테이블은 약 1.3GB였다.
- OCI Compose가 로컬 백업에도 빈 `PGBACKREST_REPO1_S3_KEY`/`KEY_SECRET`를 주입해 pgBackRest가 옵션 검증부터 실패했다. 저장소 stanza도 초기화되지 않았다.
- pgBackRest 기본 접속 역할 `postgres`와 실제 `POSTGRES_USER`가 달랐다. PostgreSQL 공식 entrypoint는 서버 실행 전에 `POSTGRES_USER`를 unset하므로 별도의 `PGBACKREST_PG1_USER` 전달이 필요하다.

## 조치

- 미사용 빌드 캐시만 정리(2GB 보존). 이미지·DB/Redis 볼륨·주문/체결 데이터는 삭제하지 않았다.
- `deploy/oci/pgbackrest-wrapper.sh`에서 비어 있는 선택적 S3 변수만 제거하고 `/usr/bin/pgbackrest`로 전달한다. 실제 S3 값은 유지한다.
- Compose에 명시적인 DB 사용자 설정과 wrapper 마운트를 추가했다. 배포 시 wrapper 실행 권한을 설정한다.
- stanza-create 후 WAL 보관을 재개했다. 낮은 압축 수준과 2개 프로세스의 비동기 보관을 사용한다. 수동 WAL 삭제나 archive_command 무시 처리는 하지 않았다.
- 백업과 stanza 작업은 OS 사용자 postgres로 실행해 저장소 파일 소유권을 통일한다.
- bootstrap은 DB healthy 대기와 stanza 초기화를 확인하고, 성공한 빌드의 불필요한 캐시를 정리한다.
- 로컬 저장소는 6시간 간격 차등 백업/매일 03:30 KST 전체 백업으로 변경했다. 전체 백업 2개·차등 6개를 보관하고 연속 WAL은 최신 차등 백업부터 유지한다. 오래된 백업 시점 복원은 가능하지만 그 사이 임의 시점 복구(PITR)는 보장하지 않는다. 기존 주간 전체 백업 사이의 모든 WAL을 보관하면 작은 로컬 디스크가 다시 고갈될 수 있기 때문이다. 이 변경 당시 기존 성공 백업은 없었다.

WAL은 보관 성공 후 PostgreSQL checkpoint 시 재사용/제거된다. `.ready` 파일을 지우거나 `pg_wal`을 직접 정리하지 않는다.

로컬 백업은 같은 디스크에 있으므로 디스크 자체 장애를 보호하지 못한다. 운영 기간이 늘면 DB·백업 증가량과 보존 기간을 함께 검토하고 외부 백업 저장소를 구성해야 한다. 백업 타이머의 성공 여부도 확인한다.
